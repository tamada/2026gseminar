# 受講生向け：welfare-time の good first issue に取り組むときの注意

先端情報学セミナーD（玉田担当分）の受講生向けのドキュメントです。
対象の [welfare-time](https://github.com/tamadalab/welfare-time) は、授業のために存在するプロジェクトではなく、実際に公開されている OSS です。授業では、これを題材にして、GitHub での開発を体験します。

## 最初に読むもの

取り組む前に、次の2つを読んでください。これらは、授業とは関係なく、このプロジェクトに参加するすべての人が従うルールです。

- [CONTRIBUTING.md](https://github.com/tamadalab/welfare-time/blob/main/CONTRIBUTING.md)：貢献の流れ、変更の書き方、PR の書き方、AI 利用ポリシー
- [CODE_OF_CONDUCT.md](https://github.com/tamadalab/welfare-time/blob/main/CODE_OF_CONDUCT.md)：行動規範

## 課題の内容

- good first issue の中から**1つ**を選び、Pull Request を出す。
- Issue には修正方法のヒントが書かれています。まずはその通りに進めてください。
- 実習回：2026-11-07 (Sat)
- 締切：**2026-11-14 (Sat) 13:15**（次回のセミナー開始時間まで）
- 出された PR は、玉田がレビューします。目標は、PR が **Approve されること**です。

## Issue の選び方

1. [good first issue の一覧](https://github.com/tamadalab/welfare-time/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22)を見る。
2. 自分で取り組めそうなものを選ぶ。
3. Issue に「取り組みます」とコメントする。
4. すでに宣言している人がいる Issue は選ばない（取り合いを避けるため）。
5. 取り組めなくなったら、Issue に「取り下げます」とコメントする。
6. 同じファイルを触る Issue は、他の人の PR とぶつかることがあります。ぶつかったら、後から出した人が最新の `main` を取り込んで直します。これも体験の一部です。

Issue は受講生の人数より多く用意してあります。困ったら、早めに教員に相談してください。

## 提出するもの

提出は2つです。

1. **GitHub 上の Pull Request**
2. **Moodle の課題** に、次の内容を書く
   - PR の番号
   - GitHub のアカウント名
   - 取り組んだ感想
   - 下の「AI の利用」に書く内容

### AI の利用

AI の利用は、かまいません。その場合、**自分で行った範囲と、AI に任せた範囲**を、はっきり書いてください。

> 例：「コード修正は自分で行い、レビューは AI に任せた。commit メッセージと PR の文面は、AI に草案を書いてもらった」

- 同じ内容を、PR の本文にも書いてください（CONTRIBUTING.md の AI 利用ポリシーに従う）。
- AI を使わなかった場合は、「使っていない」と書いてください。
- レビューで質問されたときに、自分の言葉で説明できる状態にしておいてください。

## 授業としての約束

- 他の受講生の PR やコメントにも、行動規範が適用されます。
- 他の人の PR を、自分の成果として出さないでください。
- 困ったときは、1人で抱えずに、教員か周りの人に聞いてください。
- 実際に公開されているリポジトリです。操作を誤って、他の人に迷惑をかけないよう、次のことに注意してください。
  - `main` ブランチに直接 push しない。
  - 自分の Fork でブランチを作って作業する。
  - 1つの PR で、1つの Issue だけを扱う。

## 評価

主に、次の観点で評価します。

1. **PR の中身**
   - Issue の範囲だけを変更しているか。ついでの修正が混ざっていないか。
   - CI（`just test`）が成功しているか。
   - レビューの結果、Approve されたか。
2. **書いた文章**
   - PR のタイトルと本文に、概要、関連 Issue、確認方法、AI の利用が書かれているか。
   - commit メッセージが、何をなぜ変えたかの分かるものになっているか。
3. **OSS 開発の作法**
   - 着手宣言をしてから取り組んだか。
   - レビューの指摘に、同じブランチへの追加で対応したか。
   - 行動規範に沿ったやり取りをしているか。
4. **Moodle の提出**
   - PR の番号、GitHub のアカウント名、感想、AI の利用が書かれているか。

AI を使ったこと自体が、評価を下げることはありません。申告がないことや、自分で確認していないことは、評価を下げます。

レビューで差し戻されることもあります。対応する時間を見込んで、早めに PR を出してください。
